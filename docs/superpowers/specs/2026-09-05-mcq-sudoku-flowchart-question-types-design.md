# ข้อสอบ MCQ แบบซูโดกุและผังงาน

วันที่: 2026-09-05

ต่อจาก [การสร้างข้อสอบ MCQ ทีละข้อ](2026-09-05-mcq-builder-one-question-at-a-time-design.md)

## ปัญหา

ข้อสอบ MCQ วัดได้แค่ความจำกับความเข้าใจ ส่วนการลงมือทำจริง — เติมซูโดกุ ต่อผังงาน — อยู่ในด่านแยกคนละประเภท ครูที่อยากออกข้อสอบหนึ่งชุดที่มีทั้งข้อความรู้และข้อลงมือทำจึงทำไม่ได้ ต้องสร้างสองด่านแล้วให้นักเรียนเดินสองรอบ คะแนนก็แยกกัน

## การตัดสินใจเชิงออกแบบ

| เรื่อง | เลือก | เหตุผล |
|---|---|---|
| รูปแบบการรวม | `question_type` ใหม่ 2 ค่า | ระบบมีจุดเสียบชนิดคำถามอยู่แล้ว 4 จุด (`compute_is_draft`, ฟอร์มครู, หน้าเล่น, ตัวตรวจ) เพิ่มค่าใหม่ไม่ต้องคิดกลไกใหม่ |
| ที่เก็บโจทย์ | `question_metadata` (JSON) | ตามที่ `matching`/`categorize` ทำ ไม่ต้อง migrate ตาราง |
| ไม่ใช้ตาราง `sudoku_puzzles` | เก็บใน metadata แทน | ตารางนั้นผูก `mission_id` แบบหนึ่งด่านต่อหนึ่งปริศนา ถ้าเอามาใช้ต้องแก้ FK และไปพันกับด่านซูโดกุเดิม |
| นักเรียนทำอะไร | ลงมือเล่นจริงในข้อนั้น | ไม่ใช่แค่ดูภาพประกอบแล้วเลือก ก. ข. ค. ง. |
| โหมดผังงาน | ต่อเส้นอย่างเดียว บล็อกให้มา | ตรงกับด่านผังงานที่นักเรียนคุ้นแล้ว และทำให้ id ของโหนดตรงกับเฉลยเสมอ จึงเทียบเส้นกันได้ |
| การให้คะแนน | บางส่วนตามสัดส่วนที่ทำถูก | ข้อพวกนี้กินเวลาหลายนาที ถ้าตัดสินถูก/ผิดล้วนจะเสียแรงเปล่าเมื่อพลาดช่องเดียว |
| เกณฑ์ผ่าน | เปลี่ยนทั้งระบบไปคิดจาก XP | ดูหัวข้อถัดไป |
| การใบ้ | ปิด `enable_guidance` เสมอ | เป็นการวัดผล ไม่ใช่การฝึก ด่านซูโดกุเดิมยังเปิดใบ้ได้ตามเดิม |
| ตัวตรวจ | รวมเป็นฟังก์ชันเดียว | ดูหัวข้อ "รวมตัวตรวจที่ซ้ำ" |

## เกณฑ์ผ่านเปลี่ยนไปคิดจาก XP

`finalize_mcq` ([mcq_routes.py:345](../../../backend/mcq_routes.py)) คิดเปอร์เซ็นต์จาก

```
percentage = จำนวนข้อที่ is_correct ÷ จำนวนข้อทั้งหมด
```

สูตรนี้ใช้กับคะแนนบางส่วนไม่ได้ นักเรียนที่เติมซูโดกุถูก 5 จาก 6 ช่องจะได้ `is_correct = False` แปลว่าข้อนั้นนับเป็นศูนย์ต่อเกณฑ์ผ่าน ทั้งที่ได้ XP มาแล้ว และเนื่องจาก XP จะถูกบันทึกจริงก็ต่อเมื่อ `is_passed` เป็นจริง คะแนนบางส่วนจึงอาจสูญไปทั้งก้อน

เปลี่ยนเป็น

```
percentage = Σ xp_awarded ÷ Σ xp_points ของข้อที่ไม่ใช่ร่าง
```

**ผลกระทบกับข้อสอบเดิม:** ชุดที่ทุกข้อตั้ง XP เท่ากันจะได้ผลเหมือนเดิมทุกประการ ส่วนชุดที่ตั้ง XP ไม่เท่ากันรายข้อ เกณฑ์ผ่านจะขยับ — ข้อที่ XP สูงมีน้ำหนักมากขึ้น ถือเป็นการเปลี่ยนที่ตั้งใจ เพราะการให้ครูตั้ง XP รายข้อได้แต่ไม่เอาไปใช้ถ่วงน้ำหนักนั้นขัดกับสิ่งที่ครูคาดอยู่แล้ว

`correct_answers` ยังคงนับเฉพาะข้อที่ได้เต็ม และยังใช้แสดง `score_text` เป็น "ถูก x จาก y ข้อ" ตามเดิม

## โครงข้อมูล

ไม่มีตารางใหม่ ไม่มีคอลัมน์ใหม่

### `question_metadata` ของข้อซูโดกุ

```json
{
  "size": 4,
  "box_rows": 2,
  "box_cols": 2,
  "symbol_set": ["circle", "square", "triangle", "star"],
  "render_mode": "icon",
  "given_grid": [[0, -1, -1, 3], ...],
  "solution_grid": [[0, 1, 2, 3], ...]
}
```

ฟิลด์ชุดเดียวกับ `SudokuPuzzle` ยกเว้น `enable_guidance` (ข้อสอบปิดเสมอ), `max_attempts` และ `min_xp_to_pass` (คุมที่ระดับด่านอยู่แล้ว) `-1` คือช่องว่างตาม convention เดิมทั้งระบบ

### `question_metadata` ของข้อผังงาน

```json
{
  "nodes": [{"id": "n1", "type": "start", "position": {...}, "data": {"label": "เริ่ม"}}],
  "edges": [{"source": "n1", "target": "n2", "label": "จริง"}]
}
```

รูปแบบเดียวกับ `Mission.solution_nodes` / `solution_edges` เพื่อให้ `validate_flowchart` เดิมกินได้โดยไม่ต้องแปลง

### คำตอบนักเรียน

ลง `MCQUserAnswer.answer_data` ที่มีอยู่แล้ว — ซูโดกุเป็น grid 2 มิติ ผังงานเป็นลิสต์ edges `selected_choice_id` เป็น `NULL` เหมือนชนิดที่ไม่ใช่ตัวเลือก

## การให้คะแนนบางส่วน

แต่ละชนิดคืน `(ถูก, เต็ม)` เป็นจำนวนเต็ม แล้วคิดคะแนนเป็น

```
xp_awarded = (ถูก × xp_points + เต็ม // 2) // เต็ม     # ปัดครึ่งขึ้น
is_correct = (ถูก == เต็ม)
```

**ห้ามตัดสิน `is_correct` จาก `ratio == 1.0`** เพราะการหารทศนิยมให้ค่าอย่าง `0.9999999` ได้ ต้องเทียบจำนวนเต็มตรง ๆ ด้วยเหตุผลเดียวกัน การคิด `xp_awarded` ก็ทำด้วยเลขจำนวนเต็มล้วน ไม่ผ่าน float

`xp_awarded` เป็น Integer อยู่แล้วจึงเก็บคะแนนบางส่วนได้ทันที และอ่านสัดส่วนย้อนกลับได้จาก `xp_awarded ÷ xp_points` โดยไม่ต้องเพิ่มคอลัมน์

### ซูโดกุ

```
ถูก  = ช่องที่ครูเว้นว่างและนักเรียนเติมตรง solution_grid
เต็ม = จำนวนช่องว่างทั้งหมดในโจทย์
```

ช่องที่นักเรียนปล่อยว่างไว้ (`-1`) นับเป็นผิด ไม่ใช่ข้อยกเว้น นักเรียนจึงส่งข้อที่ทำไม่เสร็จมาเก็บคะแนนเท่าที่ทำได้

ถ้านักเรียนแก้ช่องที่ครูให้มา (`given_grid[r][c] != -1` แต่ค่าไม่ตรง) ให้ `ถูก = 0` ทั้งข้อ ตามที่ `submit_puzzle` เดิมทำกับ tampering — คำตอบที่ส่งมาเปลี่ยนโจทย์ไปแล้ว จะให้คะแนนบางส่วนไม่ได้

ตรวจกับ `solution_grid` รายช่อง ไม่ใช่ `validate_board` เพราะ `validate_board` บอกได้แค่ว่าผิดกฎตรงไหน ไม่ได้บอกว่าแต่ละช่องถูกหรือไม่ ซึ่งจำเป็นสำหรับคะแนนบางส่วน

### ผังงาน

```
ถูก  = |เส้นเฉลย ∩ เส้นที่นักเรียนต่อ|
เต็ม = |เส้นเฉลย ∪ เส้นที่นักเรียนต่อ|
```

เทียบเป็นเซ็ตของ `(source, target, label)` ตามที่ `extract_connections` ใน [engine.py](../../../backend/engine.py) ทำอยู่

ต้องหารด้วย union ไม่ใช่จำนวนเส้นเฉลย มิฉะนั้นนักเรียนลากเส้นเชื่อมทุกคู่ที่เป็นไปได้จะครอบคลุมเฉลยทั้งหมดและได้คะแนนเต็มทันที การหารด้วย union ทำให้เส้นเกินหักคะแนนไปด้วย

## ปริศนาซูโดกุต้องมีคำตอบเดียว

การให้คะแนนรายช่องโดยเทียบกับ `solution_grid` จะไม่เป็นธรรมถ้าปริศนามีคำตอบมากกว่าหนึ่ง นักเรียนที่เติมได้ถูกต้องตามกฎทุกช่องแต่เป็นคนละคำตอบกับที่ครูวางไว้จะถูกหักคะแนน

ตอนบันทึกข้อ backend เรียก `count_solutions(given_grid, box_cols, box_rows, limit=2)` จาก [sudoku_solver.py](../../../backend/sudoku_solver.py) ถ้าได้ไม่เท่ากับ 1 ให้ตอบ 400 พร้อมข้อความบอกครูว่าต้องเปิดเผยช่องเพิ่ม ตรวจฝั่ง server เท่านั้น ฝั่งหน้าเว็บเรียกซ้ำเพื่อเตือนก่อนกดบันทึกได้ แต่ตัวตัดสินอยู่ที่ backend

## รวมตัวตรวจที่ซ้ำ

logic ตรวจคำตอบเขียนซ้ำสองที่ — `submit_mcq` ([mcq_routes.py:894](../../../backend/mcq_routes.py)) กับ `submit_mcq_single` ([mcq_routes.py:1152](../../../backend/mcq_routes.py)) การเพิ่มสองชนิดใหม่แปลว่าเขียนโค้ดเดียวกันสองรอบ และเป็นรูปแบบเดียวกับบั๊กที่คอมเมนต์ในไฟล์บันทึกไว้แล้วเรื่อง `finalize_mcq` ที่เคยมีสองเส้นทางให้ XP แล้วใช้คีย์ `source` ไม่ตรงกัน

ดึงเป็นฟังก์ชันเดียว วางไว้ข้าง `compute_is_draft`:

```python
def grade_answer(question, choice_id, answer_data):
    """คืน (is_correct, xp_awarded, correct_choice_id)"""
```

ทั้งสอง endpoint เรียกตัวนี้ ชนิดใหม่จึงเสียบที่เดียว เป็นการแก้ที่จำเป็นต่องานนี้โดยตรง ไม่ใช่การรื้อเพิ่ม

## Backend ที่ต้องแก้

| ไฟล์ | สิ่งที่ทำ |
|---|---|
| `mcq_routes.py` | เพิ่ม `grade_answer` แล้วให้ `submit_mcq` / `submit_mcq_single` เรียกใช้ · เพิ่มสาขา `sudoku` / `flowchart` ใน `compute_is_draft` · ตรวจ metadata ตอนบันทึกข้อ · เปลี่ยนสูตรใน `finalize_mcq` |
| `engine.py` | เพิ่ม `flowchart_score(solution_edges, student_edges)` และ `sudoku_score(meta, grid)` ข้าง `validate_flowchart` โดยยก `extract_connections` ออกมาระดับโมดูลเพื่อใช้ร่วมกัน ทั้งคู่คืน `(ถูก, เต็ม)` เป็นจำนวนเต็ม |

### เกณฑ์ข้อร่าง

ข้อที่ยังไม่ครบต้องเป็นร่าง นักเรียนจะได้ไม่เห็นและไม่ถูกนับเป็นคะแนนเต็ม

- **ซูโดกุ** — `solution_grid` ต้องเต็มไม่มี `-1` · `given_grid` ต้องมีช่องว่างอย่างน้อย 1 ช่อง · ขนาดกริดต้องตรงกับ `size` ทั้งสองกริด · `symbol_set` ต้องมีสมาชิกเท่ากับ `size`
- **ผังงาน** — `nodes` อย่างน้อย 2 · `edges` อย่างน้อย 1 · ทุก `source`/`target` ต้องเป็น id ที่มีอยู่ใน `nodes`

### การตรวจ metadata ตอนบันทึก

`question_metadata` มาจาก client จึงเชื่อไม่ได้ ตรวจก่อนเขียนเสมอ เหตุผลเดียวกับที่ `content_blocks` มี `_clean_node`:

- ค่าในกริดต้องเป็น int ในช่วง `-1` ถึง `size - 1`
- `size` ต้องเท่ากับ `box_rows × box_cols` และไม่เกิน 9 (`validate_board` วนตามขนาดนี้)
- `render_mode` ต้องเป็น `icon` หรือ `number`
- `nodes` ของผังงานต้องไม่เกิน 50 โหนด กันคำถามที่หนักจนเรนเดอร์ไม่ไหว
- `label` ของ edge รับเฉพาะ `จริง` `เท็จ` หรือค่าว่าง ตามที่ `FlowBuilder` สร้าง

## Frontend ที่ต้องแก้

### ฟอร์มครู

`QuestionForm.tsx` 431 บรรทัด การยัดทั้งกริดและแคนวาสเข้าไปจะทำให้ไฟล์ใหญ่จนแก้ยาก แยกออกเป็นสองไฟล์ที่รับ-คืนแค่ `question_metadata` ก้อนเดียว `QuestionForm` เหลือหน้าที่เลือกว่าจะ render ตัวไหน

- `components/mcq/editors/SudokuQuestionEditor.tsx` — ใช้ `SudokuBoard` เดิมได้ตรง ๆ เพราะเป็น presentational ล้วน props สะอาด ครูเลือกขนาด → วางเฉลยให้เต็มด้วย `SymbolPalette` → สลับเป็นโหมดเจาะช่องว่างแล้วกดช่องที่จะซ่อน
- `components/mcq/editors/FlowchartQuestionEditor.tsx` — ReactFlow + `Toolbox` + `CustomNodes` + `WaypointEdge` เดิม ครูวางบล็อกและลากเส้นเฉลย เหมือน `TeacherFlowBuilder` แต่ย่อลงมาอยู่ในการ์ดของข้อ

เพิ่มสองตัวเลือกใน `<select>` ชนิดคำถาม และป้ายชื่อใน `TYPE_LABEL` ของ `QuestionList`

### หน้าเล่นของนักเรียน

`StudentMCQPlayer.tsx` 993 บรรทัดแล้ว แยกส่วนตอบออกเป็น

- `components/mcq/answers/SudokuAnswer.tsx` — `SudokuBoard` + `SymbolPalette` โดย `enableGuidance={false}` และ `conflictCells={[]}` เพราะข้อสอบไม่ใบ้
- `components/mcq/answers/FlowchartAnswer.tsx` — ReactFlow โหมดปริศนา `nodesDraggable` เปิดไว้ให้จัดวางได้ แต่เพิ่ม/ลบบล็อกไม่ได้ ต่อเส้นได้อย่างเดียว

ตำแหน่งบล็อกถูกสลับตอนแสดงผลด้วยสูตรเดียวกับ `FlowBuilder` (`x = 100 + (i % 3) * 150`, `y = 100 + floor(i / 3) * 100`) โดย **id ของโหนดคงเดิมจากเฉลย** จึงเทียบเส้นกันได้ตรง ตำแหน่งไม่เกี่ยวกับการตรวจ

คำตอบเก็บเข้า `answers` state ที่มีอยู่แล้วผ่าน `answer_data` เหมือน `categorize` ไม่ต้องเพิ่มกลไกบันทึกใหม่

### หน้าเฉลยและหน้าครูดูผล

- ในหน้าเล่น หลังตอบแล้วแสดงว่าได้ XP เท่าไรจากเต็มเท่าไร และเฉลย (กริดที่ถูก / เส้นที่ถูก) แบบอ่านอย่างเดียว
- `StudentMCQView.tsx` ให้ครูเห็นกริดและผังงานที่นักเรียนทำจริง ใช้คอมโพเนนต์ตอบตัวเดียวกันโดยส่ง `disabled`

## ขอบเขต

**ทำ:** ครูสร้างข้อซูโดกุและข้อผังงานในฟอร์มข้อ · นักเรียนเล่นในข้อนั้น · คะแนนบางส่วน · เกณฑ์ผ่านคิดจาก XP · ครูดูผลรายคน

**ไม่ทำ (YAGNI):** จำกัดเวลารายข้อ (ใช้เวลารวมของด่านตามเดิม) · สุ่มลำดับสำหรับสองชนิดนี้ · ให้ครูเปิดการใบ้ต่อข้อ · แก้ด่าน `sudoku` / `flowchart` เดิม · นำเข้าโจทย์จากด่านที่สร้างไว้แล้ว

## ความเสี่ยง

| ความเสี่ยง | การรับมือ |
|---|---|
| เกณฑ์ผ่านของข้อสอบเดิมขยับ | ตั้งใจให้เกิด · ชุดที่ XP เท่ากันทุกข้อไม่กระทบ · ต้องแจ้งครูก่อนใช้จริง |
