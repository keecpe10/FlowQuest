# สร้างข้อสอบ MCQ ทีละข้อ พร้อมแถบรายการข้อด้านข้าง

วันที่: 2026-09-05

## ปัญหา

หน้าสร้างข้อสอบ [TeacherMCQBuilder.tsx](../../../frontend/src/pages/TeacherMCQBuilder.tsx) วางคำถามทุกข้อไว้ในหน้าเดียวเรียงยาวลงไป ครูต้องเลื่อนหาข้อที่ต้องการเอง และมีปุ่มบันทึกปุ่มเดียวที่ส่งข้อสอบทั้งชุดขึ้นไปพร้อมกัน

สถานะเดิมของแต่ละส่วน:

| ส่วน | สถานะเดิม |
|---|---|
| หน้าครู | คำถามทุกข้อกางอยู่ในหน้าเดียว 637 บรรทัด รวม UI ของข้อสอบทั้ง 5 ชนิดไว้ในไฟล์เดียว |
| บันทึก | มีทางเดียวคือ `PUT /api/v1/mcq/<mid>/questions` ส่งทั้งชุด [mcq_routes.py:417](../../../backend/mcq_routes.py) |
| วิธีบันทึก | `MCQQuestion.query.filter_by(mission_id=...).delete()` แล้วสร้างใหม่ทั้งหมด |
| ผลข้างเคียง | `mcq_user_answers.question_id` เป็น `ondelete='CASCADE'` [models.py:288](../../../backend/models.py) ทุกครั้งที่ครูกดบันทึก **คำตอบที่นักเรียนทำไปแล้วหายทั้งด่าน** และ `question_id` เปลี่ยนใหม่หมด |
| ลำดับตัวเลือก | `MCQChoice.query.filter_by(question_id=...).all()` ไม่มี `ORDER BY` [mcq_routes.py:357](../../../backend/mcq_routes.py) ลำดับขึ้นกับ DB |

ปัญหาคำตอบหายยังพอทนได้ตอนนี้เพราะครูกดบันทึกครั้งเดียวตอนจบ แต่รูปแบบ "ทีละข้อแล้วบันทึก" จะกดบันทึกบ่อยขึ้นมาก ถ้าใช้ API เดิมต่อไปปัญหานี้จะกลายเป็นเรื่องใหญ่ทันที

## การตัดสินใจเชิงออกแบบ

| เรื่อง | เลือก | เหตุผล |
|---|---|---|
| ความหมายของ "บันทึก" | บันทึกขึ้นเซิร์ฟเวอร์ทันทีรายข้อ | ตรงกับที่ครูคาดหวังจากปุ่มบันทึก ปิดเบราว์เซอร์ไปงานไม่หาย |
| รูปแบบ API | เพิ่ม `POST` / `PUT /<qid>` / `DELETE /<qid>` **ข้าง ๆ** PUT ทั้งชุดเดิม | PUT ทั้งชุดมี [test_mcq_blocks.py](../../../backend/test_mcq_blocks.py) ผูกอยู่หลายเคส ต้องคงไว้ · แก้ข้อไหนแตะแค่ข้อนั้น `question_id` เดิมอยู่ครบ คำตอบนักเรียนจึงรอด |
| ทางเลือกที่ไม่เอา | `PATCH` เดียวรับลิสต์ operation | ยืดหยุ่นเกินความจำเป็น ไม่มีใครใช้ความยืดหยุ่นนั้น |
| ตัวเลือกตอนแก้ข้อ | อัปเดต **ตามตำแหน่ง** ไม่ลบทิ้งสร้างใหม่ | `mcq_user_answers.selected_choice_id` เป็น `ondelete='SET NULL'` ถ้าสร้างตัวเลือกใหม่ นักเรียนจะเสียข้อมูลว่าเลือกข้อไหนไป (คะแนนที่ตรวจแล้วยังอยู่ เพราะ `is_correct`/`xp_awarded` เก็บแยก) กรณีปกติมี 4 ตัวเลือกเท่าเดิมจึงคง `choice_id` ได้ทั้งหมด |
| ข้อที่กรอกไม่ครบ | บันทึกเป็น "ร่าง" ได้ แต่นักเรียนไม่เห็น | ครูจดโจทย์ค้างไว้ก่อนแล้วค่อยกลับมาเติมตัวเลือกได้ ซึ่งเป็นพฤติกรรมที่รูปแบบทีละข้อชวนให้ทำ โดยไม่มีทางที่ข้อกรอกไม่ครบจะหลุดไปถึงนักเรียน |
| ใครตัดสินว่าเป็นร่าง | backend คำนวณเองทุกครั้งที่เขียน ครูส่งค่ามาเองไม่ได้ | แหล่งความจริงมีที่เดียว หน้าเว็บปลอมสถานะไม่ได้ |
| งานค้างตอนสลับข้อ | เตือนก่อน ให้เลือกบันทึก/ทิ้ง/ยกเลิก | ครูควบคุมได้เอง ไม่มีอะไรหายโดยไม่รู้ตัว และไม่ต้องมีข้อค้างซ่อนอยู่หลายข้อพร้อมกัน |
| โครงไฟล์หน้าครู | แยกเป็นหน้าหลัก + แถบรายการ + ฟอร์มข้อเดียว | ไฟล์เดิมโตเกินไปแล้ว การเปลี่ยนเป็น list-detail เป็นจังหวะที่ควรแยก แต่ละไฟล์จะมีหน้าที่เดียว |

## ขอบเขต

**ทำ:** ครูสร้าง/แก้/ลบข้อสอบทีละข้อและบันทึกขึ้นเซิร์ฟเวอร์รายข้อ; แถบด้านข้างแสดงรายการข้อที่มีอยู่ (เลขข้อ โจทย์ย่อ ชนิดข้อ และสัญลักษณ์ข้อร่าง) คลิกเพื่อเปิดแก้; เตือนเมื่อมีงานค้าง; ข้อที่ยังกรอกไม่ครบเก็บเป็นร่างและซ่อนจากนักเรียนทุกเส้นทาง

**ไม่ทำ (YAGNI):**

- **เรียงลำดับข้อใหม่ด้วยการลาก** — ไม่ได้ขอมาในรอบนี้ ถึงแถบด้านข้างจะชวนให้ทำก็ตาม (โปรเจกต์มี `@dnd-kit` อยู่แล้วถ้าจะเพิ่มทีหลัง)
- **route ย่อยรายข้อ** (`/questions/:qid`) — ลิงก์ตรงถึงข้อไม่ใช่สิ่งที่ต้องการตอนนี้
- **บันทึกอัตโนมัติ** — ครูเลือกให้เตือนแทน
- **กันไม่ให้เปิดด่านที่ยังมีข้อร่าง** — คนละเรื่องกับงานนี้ ข้อร่างถูกซ่อนจากนักเรียนอยู่แล้วจึงไม่มีอะไรพัง
- **ย้อนข้อมูลข้อเดิมให้เป็นร่าง** — ข้อที่มีอยู่ทั้งหมดยังคงสถานะปกติ ดูหัวข้อ Migration

## นิยาม "ข้อร่าง"

ข้อร่างคือข้อที่ยังกรอกไม่ครบตามเกณฑ์ด้านล่าง backend ตรวจเองแล้วเขียนผลลง `is_draft` ทุกครั้งที่มีการเขียนข้อนั้น (ทั้ง `POST`, `PUT /<qid>` และ PUT ทั้งชุด)

เกณฑ์ต่อชนิดข้อ — ข้อจะ **ไม่** เป็นร่างเมื่อผ่านครบทุกข้อของชนิดตัวเอง:

| ชนิด | เงื่อนไข |
|---|---|
| ทุกชนิด | โจทย์มีเนื้อหา (ข้อความที่ไม่ว่าง หรือมีรูป) และ `xp_points` มากกว่า 0 |
| `multiple_choice` / `true_false` | ตัวเลือกทุกตัวมีเนื้อหา และมีตัวที่ทำเครื่องหมายว่าถูกอยู่ 1 ตัว |
| `fill_blank` | `question_metadata.correct_text` ไม่ว่าง |
| `matching` | `question_metadata.pairs` มีอย่างน้อย 2 คู่ และทุกคู่กรอกครบทั้งสองฝั่ง |
| `categorize` | `question_metadata.categories` อย่างน้อย 2 หมวดและตั้งชื่อครบ; `items` อย่างน้อย 2 รายการ ทุกรายการมีข้อความและระบุหมวดแล้ว |

เกณฑ์ชุดนี้ตรงกับ `validateQuestions` ที่หน้าครูใช้อยู่แล้ว [TeacherMCQBuilder.tsx:41](../../../frontend/src/pages/TeacherMCQBuilder.tsx) ฝั่งหน้าเว็บยังคงตรวจต่อไปเพื่อ**บอกรายละเอียดว่าขาดอะไรบ้าง**ระหว่างที่ครูพิมพ์ ส่วนฝั่ง backend เป็นตัวตัดสินว่านักเรียนจะเห็นข้อนั้นหรือไม่ สองฝั่งมีหน้าที่ต่างกันชัดเจน และสัญลักษณ์ในแถบด้านข้างอ่านจากค่าที่ backend ส่งกลับมาเสมอ ไม่ได้คำนวณเอง

## Migration

เพิ่มคอลัมน์เดียวบน `mcq_questions`:

```python
is_draft = db.Column(db.Boolean, nullable=False, server_default='false', default=False)
```

`server_default='false'` ทำให้ **ข้อสอบที่มีอยู่ทุกข้อยังแสดงเหมือนเดิมเป๊ะ** ไม่มีข้อไหนหายไปจากสายตานักเรียนตอน migrate แม้บางข้ออาจกรอกไม่ครบตามเกณฑ์ใหม่ก็ตาม — ข้อเหล่านั้นเปิดใช้งานอยู่แล้ววันนี้ การซ่อนมันกะทันหันจะเป็นการเปลี่ยนพฤติกรรมที่ครูไม่ได้สั่ง ข้อเดิมจะได้สถานะที่คำนวณจริงก็ต่อเมื่อครูเปิดเข้าไปแก้และกดบันทึก

## Backend

### endpoint ที่เพิ่ม

ทั้งสามตัวตรวจสิทธิ์ชุดเดียวกับ PUT เดิม: ต้องล็อกอิน, mission ต้องมีอยู่และเป็นชนิด `mcq`, และผู้ใช้ต้องเป็นครูของคอร์สนั้น (`is_course_teacher`) ตรวจ `content_blocks` ด้วย `normalize_content` ตัวเดิม และ `socketio.emit('missions_updated')` เมื่อสำเร็จ

| Method | Path | พฤติกรรม |
|---|---|---|
| `POST` | `/api/v1/mcq/<mid>/questions` | สร้าง 1 ข้อ `order_index` = ค่ามากสุดที่มีอยู่ + 1 คืนข้อที่สร้างพร้อม `question_id`, `choices[].choice_id` และ `is_draft` · 201 |
| `PUT` | `/api/v1/mcq/<mid>/questions/<qid>` | แก้ในที่ `question_id` เดิมอยู่ครบ คืนข้อที่แก้แล้วในรูปแบบเดียวกับ POST · 200 |
| `DELETE` | `/api/v1/mcq/<mid>/questions/<qid>` | ลบข้อนั้น แล้วจัด `order_index` ของข้อที่เหลือใหม่ให้ต่อเนื่องจาก 0 · 200 |

`<qid>` ที่ไม่ได้อยู่ใน mission นั้นให้ตอบ 404 (ไม่ใช่แค่เช็คว่า `question_id` มีอยู่จริง) เพื่อไม่ให้ครูของคอร์สหนึ่งแก้ข้อของอีกคอร์สได้ด้วยการเดาเลข

`POST` และ `PUT /<qid>` รับ payload หน้าตาเดียวกับสมาชิกหนึ่งตัวใน `questions` ของ PUT ทั้งชุด (`content_blocks`, `question_type`, `question_metadata`, `xp_points`, `explanation`, `choices[]`) ฟิลด์ `is_draft` ที่ส่งมาจะถูกเพิกเฉย

### การอัปเดตตัวเลือกตามตำแหน่ง

`PUT /<qid>` เทียบตัวเลือกเดิมกับที่ส่งมาทีละตำแหน่ง โดยเรียงตัวเลือกเดิมด้วย `choice_id` เสมอ:

- ตำแหน่งที่มีทั้งของเดิมและของใหม่ → เขียนทับค่าลงแถวเดิม `choice_id` ไม่เปลี่ยน
- ของเดิมเกิน → ลบแถวส่วนเกิน
- ของใหม่เกิน → เพิ่มแถวใหม่

ผลคือกรณีปกติ (4 ตัวเลือกเท่าเดิม) `choice_id` อยู่ครบทุกตัว `selected_choice_id` ของนักเรียนจึงไม่กลายเป็น NULL

### การซ่อนข้อร่าง

รวมกฎไว้ที่ helper เดียวใน `mcq_routes.py` แล้วให้ทุกที่เรียกใช้ แทนการเขียน `filter_by(is_draft=False)` กระจายไป 11 จุด:

```python
def live_questions(mission_id):
    """คำถามที่นักเรียนเห็นได้จริง — ข้อร่างไม่นับ ใช้เป็นฐานของทุกการนับและทุกการให้คะแนน"""
    return MCQQuestion.query.filter_by(mission_id=mission_id, is_draft=False)
```

จุดที่ต้องเปลี่ยนมาใช้ helper นี้:

| ไฟล์ | บรรทัด | ใช้ทำอะไร |
|---|---|---|
| `mcq_routes.py` | 269 | `total_questions` ใน `finalize_mcq` |
| `mcq_routes.py` | 353 | รายการคำถามใน `get_mcq_questions` |
| `mcq_routes.py` | 714 | คำถามในหน้าครูดูความคืบหน้ารายคน |
| `mcq_routes.py` | 884 | `total_questions` ใน `complete_mcq` |
| `mcq_routes.py` | 1001 | `total_questions` ใน `manual_grade` |
| `mission_routes.py` | 75 | `total_questions` ในรายการด่าน |
| `mission_routes.py` | 315 | `total_questions` ในความคืบหน้า |
| `mission_routes.py` | 968 | คำถามที่ส่งเข้า Gemini ใน `analyze_mcq_all` |

สองจุดนี้เป็นหน้าวิเคราะห์ของครู ซึ่งก็ต้องกรองเหมือนกัน เพราะข้อร่างไม่มีใครตอบ ถ้าปนเข้าไปผลวิเคราะห์จะเพี้ยน

อีกสองจุดเป็นการค้นคำถามทีละข้อตอนนักเรียนส่งคำตอบ ซึ่งมีด่านตรวจ `question.mission_id != mission_id` อยู่แล้ว ให้เติมเงื่อนไขข้อร่างเข้าไปในด่านเดิมแทนการใช้ helper:

| ไฟล์ | บรรทัด | ใช้ทำอะไร |
|---|---|---|
| `mcq_routes.py` | 582 | ตรวจคำตอบใน `submit_mcq` — ข้ามข้อร่าง (`continue` ตามเดิม) |
| `mcq_routes.py` | 835 | ตรวจคำตอบใน `submit_mcq_single` — ตอบ 400 เหมือนข้อที่ไม่มีอยู่ |

รวมทั้งหมด 11 จุด นักเรียนไม่มีทางเห็นข้อร่างอยู่แล้ว สองจุดนี้จึงเป็นการปิดทางที่เหลือคือการยิง `question_id` เข้ามาตรง ๆ

### ทางเดียวที่เห็นข้อร่าง

`GET /api/v1/mcq/<mid>/questions?include_drafts=1` — รับเฉพาะเมื่อผู้เรียกเป็นครูของคอร์สนั้น ถ้าไม่ใช่ให้เพิกเฉยพารามิเตอร์นี้ ไม่ต้องตอบ error

ตั้งใจให้เป็น opt-in เพราะ `GET .../questions` ตัวนี้ถูกใช้ทั้งจากหน้าสร้างข้อสอบ **และ** จาก [StudentMCQPlayer.tsx:130](../../../frontend/src/pages/StudentMCQPlayer.tsx) ตอนครูกดพรีวิว ถ้ากรองด้วยเงื่อนไข "ผู้เรียกเป็นครู" เฉย ๆ ครูจะพรีวิวแล้วเห็นข้อร่างซึ่งไม่ตรงกับที่นักเรียนเห็นจริง มีแต่หน้าสร้างข้อสอบเท่านั้นที่ส่งพารามิเตอร์นี้

การตอบกลับเพิ่มฟิลด์ `is_draft` ในแต่ละข้อเมื่อผู้เรียกเป็นครู (อยู่กลุ่มเดียวกับ `explanation` และ `is_correct` ที่ส่งให้ครูเท่านั้นอยู่แล้ว)

### แก้ควบคู่: ลำดับตัวเลือก

เติม `.order_by(MCQChoice.choice_id)` ในทุกที่ที่ดึงตัวเลือก (`mcq_routes.py:357` และ `mcq_routes.py:715`) การอัปเดตตามตำแหน่งต้องอิงลำดับที่แน่นอน และโค้ดเดิมก็ถือว่าครูเห็นตัวเลือกเรียงเหมือนเดิมทุกครั้งที่โหลดอยู่แล้ว เพียงแต่ไม่เคยบังคับไว้

`QuestionList` และ `QuestionForm` ไม่รู้จัก axios และไม่รู้จัก `id` ของ mission — รับข้อมูลกับ callback ทางพรอปอย่างเดียว หน้าหลักเป็นที่เดียวที่คุยกับเซิร์ฟเวอร์

### สถานะ

| ตัวแปร | ความหมาย |
|---|---|
| `questions` | รายการข้อจากเซิร์ฟเวอร์ ใช้ทำแถบด้านข้างเท่านั้น |
| `selected` | `question_id` ของข้อที่เปิดอยู่ หรือ `'new'` เมื่อกำลังสร้างข้อใหม่ หรือ `null` เมื่อยังไม่ได้เลือก |
| `draft` | เนื้อหาของข้อที่กำลังแก้ (คนละตัวกับ `questions` เพื่อให้ทิ้งการแก้ได้) |
| `dirty` | `draft` ต่างจากที่บันทึกไว้หรือยัง |

### การไหลของงาน

1. เข้าหน้า → `GET .../questions?include_drafts=1` → เลือกข้อแรกให้อัตโนมัติ ถ้าไม่มีข้อเลยให้เข้าโหมด `'new'` ทันที
2. คลิกข้อในแถบ หรือกด "เพิ่มข้อ" → ถ้า `dirty` ให้ถามด้วย Swal สามทาง **บันทึก / ทิ้ง / ยกเลิก** แล้วค่อยสลับ (เลือกยกเลิกคือไม่สลับ)
3. กดบันทึก → ส่ง `POST` เมื่อ `selected === 'new'` มิฉะนั้น `PUT /<qid>` → เอาผลที่ตอบกลับมาปรับ `questions` และ `draft` → `dirty = false`
4. กดลบ → Swal ยืนยัน → `DELETE /<qid>` → ตัดออกจาก `questions` → เลือกข้อถัดไปให้ (ถ้าลบข้อสุดท้ายให้เลือกข้อก่อนหน้า ถ้าไม่เหลือเลยให้เข้าโหมด `'new'`)
5. กดยกเลิกในฟอร์ม → โหมด `'new'` ทิ้งข้อใหม่แล้วกลับไปที่ข้อที่เปิดอยู่ก่อนหน้า (ถ้าไม่มีให้ปล่อยฟอร์มว่าง) · โหมดแก้ข้อเดิม ย้อน `draft` กลับเป็นค่าที่บันทึกไว้ล่าสุด ทั้งสองกรณีถามยืนยันเมื่อ `dirty` เท่านั้น

การบันทึกไม่ปิดกั้นข้อที่กรอกไม่ครบ แต่ยังแสดงรายการสิ่งที่ขาดไว้ในฟอร์มเพื่อให้ครูรู้ว่าข้อนี้จะถูกเก็บเป็นร่าง

### แถวในแถบด้านข้าง

แต่ละแถวมีเลขข้อ, โจทย์ย่อ, ชนิดข้อเป็นภาษาไทย และสัญลักษณ์ ⚠️ เมื่อ `is_draft` เป็นจริง แถวที่เปิดอยู่ไฮไลต์ไว้

ขณะอยู่ในโหมด `'new'` แถบด้านข้างเพิ่มแถวชั่วคราวต่อท้ายเขียนว่า **"ข้อใหม่ (ยังไม่บันทึก)"** และไฮไลต์ไว้ ครูจะได้เห็นว่าข้อที่กำลังสร้างจะไปอยู่ตำแหน่งไหน แถวนี้ไม่มีเลขข้อและกดไม่ได้ พอบันทึกสำเร็จจึงกลายเป็นแถวปกติ

`docToPlainText(doc)` ดึงเฉพาะโหนด `text` ต่อกันแล้วตัดที่ 40 ตัวอักษร ถ้าไม่มีข้อความเลยแต่มีโหนด `image` ให้คืน `[รูปภาพ]` ซึ่งเป็นคำเดียวกับ `IMAGE_ONLY_TEXT` ที่ backend ใช้อยู่แล้ว [mcq_routes.py:34](../../../backend/mcq_routes.py) ถ้าว่างทั้งคู่ให้คืน `(ยังไม่มีโจทย์)`

### ผลพลอยได้ด้านความลื่นไหล

ฟอร์มแสดงทีละข้อ จึงมีตัวแก้ไข TipTap อยู่ในหน้าไม่เกิน 5 ตัวเสมอไม่ว่าจะมีข้อสอบกี่ข้อ อาการกระตุกที่เพิ่งแก้ไปในรอบก่อน (ตัวแก้ไข 5 ตัวต่อข้อ คูณจำนวนข้อ) จึงไม่มีทางกลับมาจากทางนี้อีก

## กรณีขอบ

| กรณี | พฤติกรรม |
|---|---|
| ครูสองคนแก้ข้อเดียวกันพร้อมกัน | คนที่กดบันทึกทีหลังทับคนแรก ไม่มีการตรวจเวอร์ชัน — เท่ากับพฤติกรรมเดิมของ PUT ทั้งชุด |
| ลบข้อที่นักเรียนตอบไปแล้ว | คำตอบของข้อนั้นหายตาม `ondelete='CASCADE'` ซึ่งเป็นสิ่งที่ตั้งใจ ส่วนคำตอบของข้ออื่นไม่กระทบ |
| แก้ข้อจนกลายเป็นร่าง ทั้งที่นักเรียนตอบไปแล้ว | ข้อหายจากสายตานักเรียนและไม่ถูกนับใน `total_questions` แต่แถว `mcq_user_answers` ยังอยู่ พอครูกรอกครบแล้วบันทึก ข้อกลับมาพร้อมคำตอบเดิม |
| เปลี่ยนชนิดข้อจาก 4 ตัวเลือกเป็น `matching` | ตัวเลือกเดิมถูกลบทั้งหมดเพราะชนิดใหม่ไม่ใช้ `choices` |
| กดบันทึกข้อใหม่สองครั้งรัว ๆ | ปิดปุ่มระหว่างที่คำขอยังไม่จบ กัน `POST` ซ้ำจนได้ข้อซ้ำ |
| ปิดแท็บทั้งที่มีงานค้าง | งานค้างหาย ไม่มีการกู้ร่าง — ตรงกับที่ตัดออกในขอบเขต |
| `include_drafts=1` จากคนที่ไม่ใช่ครู | เพิกเฉยพารามิเตอร์ ตอบเฉพาะข้อที่ไม่ใช่ร่างตามปกติ |
